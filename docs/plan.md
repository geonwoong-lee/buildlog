# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 기능을 React, FastAPI, Supabase PostgreSQL, SQLite 3로 어떤 순서에 따라 개발할지 설명합니다.

작업은 Phase 단위로 진행합니다. 한 번에는 Phase 하나만 구현하고, 해당 Phase의 자동 테스트와 직접 확인을 모두 통과한 뒤 다음 Phase로 넘어갑니다.

## 2. 확정한 기술 구성

| 구분 | 사용할 기술 | 역할 |
| --- | --- | --- |
| 프론트엔드 | React + TypeScript + Vite | 사용자가 보는 화면과 입력 처리 |
| 백엔드 | Python + FastAPI | API, 입력 검증, 로그인, 권한 처리 |
| 데이터 처리 | SQLAlchemy | SQLite 3와 PostgreSQL을 같은 모델로 사용 |
| 데이터 변경 이력 | Alembic | 데이터 구조 생성과 변경 관리 |
| 실제 서비스 DB | Supabase PostgreSQL | 실제 사용자와 기록 데이터 보관 |
| 로컬·테스트 DB | SQLite 3 | 개발 중 기능 확인과 자동 테스트 |
| 백엔드 테스트 | pytest | API, 데이터, 권한 자동 확인 |
| 프론트엔드 테스트 | Vitest + React Testing Library | 화면 동작 자동 확인 |

Supabase는 첫 버전에서 데이터베이스로 사용합니다. 회원가입과 로그인은 `spec.md`의 이메일·비밀번호 규칙에 따라 FastAPI에서 처리합니다. Supabase Auth로 기능 범위를 바꾸지 않습니다.

## 3. 개발 원칙

- `spec.md`에 없는 기능은 추가하지 않습니다.
- 화면에서 버튼을 숨기는 것만으로 권한을 처리하지 않고 FastAPI에서도 권한을 검사합니다.
- 화면과 API 양쪽에서 입력값을 확인합니다.
- 비밀번호는 안전하게 변환해서 저장하며 원문을 기록하거나 응답으로 보내지 않습니다.
- 비밀 설정값, `.env`, `.venv`, `node_modules`, 로그, 빌드 결과, 실제 SQLite 파일은 Git 기록 대상에서 제외합니다.
- SQLite 3와 Supabase PostgreSQL에서 입력 검사, 권한, 공개 범위, 검색, 정렬 결과가 같아야 합니다.
- 특정 데이터베이스에서만 동작하는 SQL은 피하고 SQLAlchemy를 통해 데이터를 처리합니다.
- 각 Phase에서 정상 동작, 경계값, 실패 상황, 권한 위반을 함께 테스트합니다.
- Git 초기화와 커밋은 별도 요청이 있기 전까지 수행하지 않습니다.

│  │  └─ services/            # 공통 업무 규칙
│  ├─ tests/                  # FastAPI와 SQLite 자동 테스트

│  │  ├─ styles/              # 공통 디자인

│  └─ vite.config.ts

└─ .gitignore

## 6. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준과 환경 확인

#### 목표

패키지나 코드를 만들기 전에 현재 컴퓨터가 확정한 기술 구성을 실행할 수 있는지 확인합니다.

#### 작업

1. `mvp.md`, `PRD.md`, `spec.md`, `plan.md`의 기능과 기술 기준이 충돌하지 않는지 확인합니다.
2. 첫 버전 제외 기능을 다시 확인합니다.
   - 이메일 확인
   - 비밀번호 찾기
   - 할 일 마감일과 중요도
   - 내 할 일 검색
   - 댓글 답글
3. Node.js와 npm 실행 여부 및 버전을 확인합니다.
4. Python 실행 여부와 버전을 확인합니다.
5. Python에서 SQLite 3 모듈을 사용할 수 있는지 확인합니다.
6. React와 FastAPI가 사용할 로컬 주소를 정합니다.
   - React: `http://localhost:5173`
   - FastAPI: `http://localhost:8000`
7. 환경 변수 이름을 정합니다.
   - 실행 환경 구분
   - 데이터베이스 연결 주소
   - 로그인 보안 키
   - 허용할 프론트엔드 주소
8. npm이 PowerShell 실행 정책 때문에 직접 실행되지 않으면 `npm.cmd`를 사용하는 방법을 기록합니다.
9. Supabase 연결값은 이 Phase에서 요구하거나 저장하지 않습니다.

#### 예상 변경 파일

- `docs/plan.md`
- 필요할 경우 `docs/setup.md` 초안
- 코드와 패키지는 아직 만들지 않음

#### 확인 방법

- Node.js, npm, Python 명령이 실행되는지 확인합니다.
- Python에서 SQLite 버전을 출력할 수 있는지 확인합니다.
- 네 개의 기준 문서에 현재 선택과 충돌하는 이전 기술 기준이 남아 있지 않은지 확인합니다.
- 아직 패키지 설치, 데이터베이스 생성, Supabase 연결을 하지 않았는지 확인합니다.

#### 완료 조건

- React, FastAPI, SQLite 3 개발을 시작하는 데 필요한 도구가 준비되어 있습니다.
- 누락된 도구가 있으면 설치가 필요한 항목과 방법을 사용자에게 알렸습니다.
- Supabase 계정 없이도 Phase 1을 시작할 수 있습니다.

### Phase 1. React와 FastAPI 프로젝트 뼈대

#### 목표

기능 없이도 React 화면과 FastAPI 서버가 각각 실행되고 서로 통신할 수 있게 합니다.

#### 작업

1. `frontend`에 React + TypeScript + Vite 프로젝트를 구성합니다.
2. `backend/.venv`에 Python 가상환경을 만듭니다.
3. FastAPI 실행에 필요한 최소 패키지를 설치하고 버전을 기록합니다.
4. `backend/app/main.py`에 FastAPI 앱을 만듭니다.
5. 서버 상태를 확인하는 최소 API를 만듭니다.
6. React 기본 화면에서 상태 확인 API를 호출해 성공 여부를 보여줍니다.
7. React 개발 주소만 FastAPI 호출을 허용하도록 설정합니다.
8. 공통 환경 설정 로더를 만들고 실제 값은 `.env`에서 읽습니다.
9. `.env.example`에는 변수 이름과 예시만 기록합니다.
10. `.gitignore`에 SQLite 파일과 Python·React 생성물을 보완합니다.
11. 프론트엔드와 백엔드의 최소 테스트 한 개씩을 추가합니다.

#### 완료 조건

- React 개발 서버와 FastAPI 개발 서버가 오류 없이 실행됩니다.
- React 화면에서 FastAPI 상태 확인 결과를 볼 수 있습니다.
- 프론트엔드와 백엔드의 최소 테스트가 통과합니다.
- Supabase 없이도 모든 확인이 가능합니다.

---

### Phase 2. 공통 데이터베이스 계층과 사용자 모델

#### 목표

같은 SQLAlchemy 모델을 SQLite 3와 Supabase PostgreSQL에서 사용할 수 있는 기반을 만들고 사용자 구조를 확정합니다.

#### 작업

1. 환경 변수의 데이터베이스 주소에 따라 연결하는 공통 DB 설정을 만듭니다.
2. SQLAlchemy 모델 공통 기반과 DB 세션 처리를 만듭니다.
3. Alembic을 `database/migrations`와 연결합니다.
4. 사용자 모델에 이메일, 비밀번호 해시, 닉네임, 운영자 여부, 가입 날짜를 정의합니다.
5. 이메일과 닉네임에 중복 방지 조건을 둡니다.
6. 닉네임 2~20자와 허용 문자 규칙을 공통 검증으로 만듭니다.
7. 첫 마이그레이션을 만듭니다.
8. SQLite 3 테스트 DB에 마이그레이션을 적용합니다.
9. 테스트가 끝날 때 독립된 SQLite DB를 정리해 테스트끼리 영향을 주지 않게 합니다.

#### 완료 조건

- 빈 SQLite 3 DB를 마이그레이션만으로 만들 수 있습니다.
- 사용자 저장, 중복 방지, 닉네임 조건 테스트가 통과합니다.
- 비밀번호 원문이 DB에 저장되지 않습니다.
- 코드에 SQLite 전용 SQL이 들어 있지 않습니다.

---

### Phase 3. 회원가입·로그인·닉네임 변경

#### 목표

React 화면과 FastAPI API를 연결해 회원 기능을 완성합니다.

#### 작업

1. 회원가입 API와 React 화면을 만듭니다.
2. 이메일 형식과 중복, 비밀번호 8~64자, 닉네임 조건을 검사합니다.
3. 회원가입 실패 시 이메일과 닉네임은 유지하고 비밀번호만 지웁니다.
4. 성공하면 로그인 화면으로 이동합니다.
5. 로그인 API와 React 화면을 만듭니다.
6. 안전한 로그인 상태를 만들고 인증이 필요한 API에서 확인합니다.
7. 로그인 실패 시 이메일은 유지하고 비밀번호만 지웁니다.
8. 로그인 성공 후 내 기록 홈으로 이동합니다.
9. 로그인하지 않은 사용자가 React 주소나 API를 직접 열어도 기록을 볼 수 없게 합니다.
10. 계정 설정에서 닉네임을 변경하게 합니다.
11. 이메일 확인과 비밀번호 찾기는 만들지 않습니다.

#### 완료 조건

- `spec.md` 2장의 경계값과 실패 동작이 모두 통과합니다.
- React에서 숨긴 기능을 API 직접 호출로 우회할 수 없습니다.
- 비밀번호 원문이 응답, 로그, DB에 나타나지 않습니다.

---

### Phase 4. 공부 기록·할 일·오류 기록 모델

#### 목표

세 기록 기능이 사용할 데이터 구조와 상태 전환 규칙을 먼저 완성합니다.

#### 작업

1. 공부 기록 모델을 만듭니다.
   - 작성자, 제목, 내용, 공개 여부, 작성·수정 날짜
2. 할 일 모델을 만듭니다.
   - 작성자, 제목, 완료 여부, 공개 여부, 작성·수정·완료 날짜
3. 오류 기록 모델을 만듭니다.
   - 작성자, 제목, 오류 내용, 해결 방법, 해결 여부, 공개 여부, 작성·수정·해결 날짜
4. 새 기록은 비공개를 기본값으로 둡니다.
5. 새 할 일은 미완료, 새 오류는 미해결을 기본값으로 둡니다.
6. 상태 변경 시 완료 날짜와 해결 날짜를 처리하는 공통 규칙을 만듭니다.
7. Alembic 마이그레이션을 만들고 SQLite 3에 적용합니다.
8. 모델과 상태 전환 테스트를 작성합니다.

#### 완료 조건

- 세 기록을 SQLite 3에 저장하고 다시 읽을 수 있습니다.
- 기본 공개·완료·해결 상태가 정확합니다.
- 완료·해결을 취소할 때 날짜 처리 규칙이 정확합니다.
- 서버를 다시 실행해도 파일 기반 SQLite 테스트 데이터가 유지됩니다.

---

### Phase 5. 공부 기록 전체 흐름

#### 목표

공부 기록의 작성, 목록, 읽기, 검색, 수정, 삭제를 React와 FastAPI로 연결합니다.

#### 작업

1. 제목 1~100자와 내용 1~5,000자를 받는 API와 화면을 만듭니다.
2. 입력 앞뒤 공백을 제거하고 공백만 있는 입력을 거부합니다.
3. 공개 여부 기본값을 비공개로 둡니다.
4. 내 기록을 최근 작성 순으로 보여줍니다.
5. 제목과 내용으로 내 기록을 검색합니다.
6. 빈 검색어는 전체 목록을 보여줍니다.
7. 상세 읽기, 수정, 삭제 확인을 만듭니다.
8. 작성자만 수정·삭제할 수 있게 API에서 확인합니다.
9. 저장·수정 실패 시 React 입력값과 기존 DB 값을 유지합니다.

#### 완료 조건

- `spec.md` 4장의 모든 확인 항목이 통과합니다.
- 다른 사용자는 비공개 공부 기록을 읽거나 변경할 수 없습니다.

---

### Phase 6. 할 일 전체 흐름

#### 목표

할 일 작성, 필터, 완료·취소, 수정, 삭제를 연결합니다.

#### 작업

1. 제목 1~100자와 공개 여부를 받는 API와 화면을 만듭니다.

3. `전체`, `남은 일`, `완료한 일` 필터를 만듭니다.
4. 완료하면 완료 날짜를 저장하고 취소하면 지웁니다.
5. 작성자만 상태 변경, 수정, 삭제할 수 있게 합니다.
6. 수정 날짜를 목록에 표시합니다.
7. 할 일 검색, 마감일, 중요도는 만들지 않습니다.

#### 완료 조건

- `spec.md` 5장의 모든 확인 항목이 통과합니다.
- 상태 변경 실패 시 화면과 DB 모두 이전 상태를 유지합니다.

### Phase 7. 오류 기록 전체 흐름

오류 기록의 작성, 검색, 필터, 해결·취소, 수정, 삭제를 연결합니다.

#### 작업

1. 제목 1~100자, 오류 내용 1~5,000자, 해결 방법 최대 5,000자를 처리합니다.

3. 해결 방법 없이 해결 상태로 바꿀 수 없게 합니다.
4. `전체`, `미해결`, `해결` 필터를 만듭니다.
5. 제목과 오류 내용으로 내 오류를 검색합니다.
6. 해결 시 해결 날짜를 저장합니다.
7. 해결을 취소하면 해결 방법은 유지하고 해결 날짜만 지웁니다.
8. 작성자만 해결 상태 변경, 수정, 삭제를 할 수 있게 합니다.

#### 완료 조건

- `spec.md` 6장의 모든 확인 항목이 통과합니다.
- 해결 방법과 해결 날짜의 상태 전환 규칙이 정확합니다.

- `spec.md` 3장과 7장의 모든 확인 항목이 통과합니다.

### Phase 13. Supabase 연결과 데이터베이스 호환성

#### 목표

SQLite 3에서 완성한 기능을 Supabase PostgreSQL에 연결하고 같은 결과가 나오는지 확인합니다.

#### 작업

1. 사용자가 만든 Supabase 프로젝트의 PostgreSQL 연결 문자열을 로컬 `.env`에 등록합니다.
2. 연결 문자열이나 비밀번호가 문서, 로그, Git 대상 파일에 들어가지 않았는지 확인합니다.
3. Alembic 마이그레이션을 빈 Supabase DB에 적용합니다.
4. 사용자, 세 기록, 댓글, 좋아요, 신고 모델이 모두 생성되는지 확인합니다.
5. SQLite 3 자동 테스트는 계속 기본 테스트로 유지합니다.
6. Supabase 전용 통합 테스트는 별도 표시하고 실제 연결값이 있을 때만 실행합니다.
7. 검색, 정렬, 중복 방지, 날짜, 공개 권한 결과를 두 DB에서 비교합니다.
8. 차이가 있으면 특정 DB용 기능을 추가하기보다 공통 규칙으로 수정합니다.

#### 완료 조건

- 같은 Alembic 변경 이력이 SQLite 3와 Supabase에 적용됩니다.
- `spec.md`의 핵심 흐름이 Supabase에서도 통과합니다.
- Supabase 비밀값이 저장소나 사용자 화면에 노출되지 않습니다.

### Phase 14. 전체 통합 확인과 실행 문서

모든 기능을 함께 검증하고 처음 실행하는 사람도 따라 할 수 있는 문서를 완성합니다.

#### 작업

1. 프론트엔드와 백엔드 자동 테스트를 한 번에 실행합니다.

3. SQLite 3와 Supabase 환경에서 핵심 시나리오를 각각 확인합니다.

5. 회원가입부터 신고까지 `spec.md`의 확인 항목을 실행합니다.
6. 설치, 환경 변수, SQLite 실행, Supabase 연결, 서버 실행, 테스트 명령을 `docs/setup.md`에 작성합니다.
7. `.env.example`에 필요한 이름만 있고 실제 비밀값이 없는지 확인합니다.
8. 실패한 항목만 수정하고 새 기능은 추가하지 않습니다.

- Supabase 연결값이 있는 사람은 같은 문서로 운영 DB를 연결할 수 있습니다.

### Phase 15. 프론트엔드와 백엔드 배포

#### 목표

React와 FastAPI를 실제 인터넷 주소에 배포하고 Supabase DB와 연결합니다.

#### 시작 전 결정

- 프론트엔드와 백엔드를 운영할 서비스는 아직 정하지 않았습니다.
- 이 Phase를 시작할 때 비용, 무료 사용 제한, 한국에서의 접속 속도를 확인해 배포 서비스를 선택합니다.
- 사용자가 해당 서비스 계정을 연결하거나 필요한 접근 권한을 제공해야 합니다.

#### 작업

1. React 운영 빌드와 FastAPI 실행 명령을 확인합니다.
2. 배포 서비스에 환경 변수를 안전하게 등록합니다.
3. 운영 FastAPI가 Supabase PostgreSQL에 연결되게 합니다.
4. 실제 프론트엔드 주소만 API 호출이 가능하도록 허용 주소를 바꿉니다.
5. HTTPS 환경에서 로그인 상태와 보안 설정을 확인합니다.
6. PC와 휴대폰에서 회원가입부터 신고까지 핵심 흐름을 확인합니다.
7. 비공개 기록과 운영자 신고 정보가 노출되지 않는지 재확인합니다.

#### 완료 조건

- 실제 주소에서 React, FastAPI, Supabase가 정상적으로 연결됩니다.
- 여러 기기에서 같은 계정과 데이터를 사용할 수 있습니다.
- `spec.md`의 핵심 흐름과 권한 검사가 운영 환경에서도 통과합니다.

## 7. Phase 진행 기록 방법

각 Phase를 마칠 때 다음 내용을 공유합니다.

| 항목 | 기록할 내용 |
| --- | --- |
| 상태 | 시작 전 / 진행 중 / 검토 중 / 완료 |
